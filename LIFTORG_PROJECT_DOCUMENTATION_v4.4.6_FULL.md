# 1. Назначение продукта

Liftorg B2B Engineering Platform — профессиональная B2B-платформа для подбора, сравнения, конфигурирования, коммерческого расчёта и запроса лифтового оборудования.

Текущий первый предметный домен — **лифтовые тяговые машины / лебёдки**.

Платформа не проектируется как обычный интернет-магазин. Основная аудитория:

- инженеры;
- проектировщики;
- технические специалисты;
- закупщики B2B;
- менеджеры Liftorg / Оператора;
- производители оборудования;
- администраторы платформы.

Главная продуктовая идея:

```text
Технические параметры проекта
        ↓
Инженерный подбор по исполнениям
        ↓
Группировка подходящих исполнений в модели
        ↓
Сравнение 2–4 моделей
        ↓
Выбор конкретного исполнения
        ↓
Техническая карточка / чертежи / фото
        ↓
Расчёт стоимости / CPQ
        ↓
Короткий коммерческий запрос ИЛИ инженерный опросник
        ↓
RFQ / коммерческое предложение
        ↓
CRM / работа менеджера / сделка
```

Дальнейшая цель заказчика — развить это ядро до общей лифтовой платформы с каталогом лифтов, производителями, контентными страницами и передачей лидов в CRM.

## 3.2. Модель и исполнение — принципиально разные сущности UX

Ключевое правило, принятое после тестирования карточек:

> **База хранит исполнения. Подбор выполняется по исполнениям. Пользовательский каталог показывает модели.**

Причина: несколько строк Excel могут иметь одинаковую модель, но отличаться техническим исполнением.

Логика:

1. каждая из 838 строк участвует в подборе отдельно;
2. после подбора прошедшие строки группируются по `manufacturer + model`;
3. пользователь видит одну карточку модели;
4. карточка показывает число доступных исполнений;
5. перед расчётом, сравнением, заказом или RFQ выбирается конкретное исполнение;
6. значения разных исполнений нельзя усреднять или объединять в вымышленную спецификацию.

Текущий результат группировки baseline — около **559 пользовательских моделей** из 838 исполнений; Nidec — около 553 моделей из 831 исполнения.

# 6. Инженерный подбор

## 6.1. Объяснимый движок PASS / UNKNOWN / FAIL

Каждый выбранный критерий оценивается отдельно:

### PASS

Значение известно и удовлетворяет условию.

### UNKNOWN

В исходнике нет значения или оно недостаточно определено.

**UNKNOWN не исключает исполнение.** Оно остаётся кандидатом и помечается «Требует уточнения».

### FAIL

Значение известно и противоречит выбранному условию.

Только FAIL исключает исполнение.

## 6.2. Почему фильтр был смягчён

Ранняя версия давала ложные нулевые результаты, потому что отсутствие высоты/размещения/другого поля фактически считалось несовпадением.

Текущее правило:

```text
известно + совпадает        → PASS
нет данных                  → UNKNOWN
известно + не совпадает     → FAIL
```

## 6.3. Сортировка результата

1. полностью подтверждённые исполнения;
2. кандидаты с минимальным количеством UNKNOWN;
3. внутри UI исполнения группируются в модель.

## 6.4. Explainability

Для результата должны быть доступны:

- `match_status`;
- `match_summary`;
- `match_checks`;
- `clarifications`;
- объяснение «почему исключено» для режима инженера/администратора.

19. **Масса**.
20. **Тип размещения** — машинное помещение / без машинного помещения.

### 8.20.1. Подтверждённое правило классификации размещения от 26.08.2026

Источник: прямое уточнение инженера/Заказчика 26.08.2026. Это правило является **подтверждённым инженерным правилом**, а не эвристикой разработчика.

Классификация:

- `Без машинного помещения (MRL)`:
  - **все лебёдки типа «Безредукторная бочонок»**;
  - плоские таблетки серии **WE 06**;
  - плоские таблетки серии **WE 10**;
  - плоские таблетки серии **WE 20**;
  - исполнения **WJC с суффиксом `-T`** (`WJC-T` в терминологии инженера).
- `В машинном помещении (MR)`:
  - **все остальные лебёдки типа «Безредукторная таблетка»**, то есть объёмные таблетки.

Приоритет данных:

1. Если для конкретной позиции администратор или исходный источник явно задал `placement_type`, это значение имеет приоритет над автоматическим правилом.
2. Иначе применяется подтверждённое правило выше.
3. Для позиций, тип которых пока не позволяет достоверно применить правило, значение остаётся неизвестным (`UNKNOWN`) и система ничего не выдумывает.

Техническая реализация baseline 4.4.4:

- правило применяется в функции `placement_type_of()`;
- при запуске выполняется безопасная миграция восстановленной SQLite-БД: пустой `placement_type` материализуется для классифицируемых позиций;
- сохраняется `placement_type_source`, чтобы администратор видел происхождение значения;
- правило работает одновременно в поиске, фильтре, карточке, API и админке;
- ручные значения не перезаписываются миграцией.

Покрытие текущей базы из 838 исполнений после применения правила:

- **498** исполнений — `Без машинного помещения`;
- **334** исполнения — `В машинном помещении`;
- **6** исполнений пока остаются без подтверждённой классификации;
- итоговое покрытие поля `placement_type`: **832 / 838**.

В 498 MRL входят 200 «бочонков» и 298 плоских таблеток по подтверждённым сериям. В 334 MR входят остальные объёмные таблетки.

- безредукторная лебёдка всегда 1 скорость;

## 7.3. Новое замечание инженера 26.08.2026 — длина троса/кабеля и форма машины

Получен отдельный комментарий:

- добавить фильтр длины — примеры **8 м, 10 м, 12 м**;
- отдельно учесть безмашинные варианты/«таблетки»;
- инженер отдельно упомянул **плоские таблетки**, пример `WE-20-2000`;
- окончательная классификация должна быть подтверждена инженером после его дополнительной проработки.

Статус: **принято в требования, требует финальной нормализации поля и источника данных перед включением в production filter engine**.

Важно не смешивать это замечание автоматически с TDNA-полем `Encoder Cable Length` (в TDNA для gearless указаны 10/20/37/50/60 м), пока инженер явно не подтвердит, что речь об одном и том же параметре.

## 7.4. Фасетное поведение — целевое UX-улучшение

После каждого выбора желательно пересчитывать доступные значения остальных фильтров и визуально отключать невозможные комбинации. Это уменьшает вероятность пустой выдачи.

# 13. Целевой CPQ по документу заказчика

## 13.1. Многострочное коммерческое предложение

Обязательная строка:

- лебёдка.

Опциональные строки:

- рама / bedplate;
- виброизоляторы;
- отклоняющий/отводной блок;
- крепёжный комплект;
- пакет чертежей;
- услуги;
- иные позиции после согласования с экспертами заказчика.

Каждая строка имеет независимо:

- цену;
- срок;
- Incoterms 2020.

## 13.2. Формула цены позиции

Целевой принцип:

```text
Базовая EXW цена
+ надбавки
- объёмные скидки
```

Скидка вендора применяется к EXW в соответствии с контрактом исходного файла.

## 13.3. EXW → DDP

Целевая структура DDP до склада Оператора:

1. EXW закупочная цена производителя;
2. экспортная упаковка и местные сборы КНР;
3. международный фрахт:
   - море;
   - железная дорога;
   - авто;
4. страхование;
5. пошлина ЕАЭС;
6. НДС страны назначения;
7. таможенный представитель;
8. банковская комиссия;
9. плата за перевод;
10. стоимость оплаты поставщику;
11. торговая наценка Оператора;
12. валютное приведение;
13. последняя миля — отдельная опция, не включается автоматически в базовую DDP.

## 13.4. Данные производителя для логистики

В «Справочнике номенклатуры» производитель должен задавать по позиции:

- закупочную цену;
- количество мест/единиц в машине или контейнере;
- длину упаковки;
- ширину упаковки;
- высоту упаковки;
- массу;
- срок производства.

Эти поля участвуют в расчёте веса/объёма и логистики.

## 13.5. Коэффициенты

Изменяются администратором без изменения кода:

- банковские комиссии;
- фиксированная плата за перевод;
- оплата поставщику;
- кредитная ставка;
- торговая наценка;
- фрахт;
- последняя миля;
- производственные/логистические сроки;
- курсы валют;
- другие коэффициенты из Excel-контракта.

Формулы при этом остаются версионированными и неизменяемыми.

## 13.6. Целевые графики оплаты по новому документу

В новом CPQ-контракте должны поддерживаться:

1. 100% предоплата;
2. 50% предоплата + 50% перед отгрузкой;
3. 100% перед отгрузкой;
4. 100% после отгрузки + 30 дней.

Для каждого графика:

- дата платежа;
- сумма;
- надбавка/дисконт стоимости денег из Excel.

Это целевой контракт. При внедрении потребуется явно сопоставить эти названия с историческими листами `Калькулятор-2.xlsx`, а не угадывать соответствие.

## 13.7. Ролевая видимость цены

### Покупатель

Видит:

- итоговую DDP;
- выбранный график оплаты;
- срок;
- RUB-индикатив, если разрешено.

Не видит:

- EXW;
- закупочную цену;
- внутреннюю наценку;
- внутренние комиссии.

### Производитель

Видит:

- собственную закупочную/EXW цену;
- наценку Оператора только в режиме просмотра, если это подтверждено финальным контрактом;
- итоговую цену продажи;
- разрешённые поля своей позиции.

### Оператор/администратор

Видит весь breakdown и коэффициенты.

## 13.8. Валюты

Целевые:

- CNY;
- USD;
- EUR;
- RUB.

Нужен подключаемый источник курса:

- обновление по расписанию;
- история курсов;
- источник меняется конфигурацией;
- система не должна быть жёстко привязана к одному национальному провайдеру.

## 13.9. Отказоустойчивость калькулятора

Если недоступен источник курсов/фрахта/ставки:

- цена скрывается как `уточняется`, либо
- применяется последнее достоверное значение с явной пометкой;
- событие логируется;
- возможен retry;
- старое КП не пересчитывается задним числом.

## 13.10. Версии калькулятора

Каждое сформированное КП должно иметь:

- `calculator_version`;
- снимок коэффициентов;
- курс;
- timestamp;
- входные данные;
- итог.

Пересчёт новой версией не изменяет старое КП.

# 14. RFQ

## 14.1. Целевая сущность RFQ

RFQ должен хранить:

- технические параметры;
- выбранное исполнение/модели;
- количество;
- желаемый срок;
- валюту;
- дедлайн подачи КП;
- график оплаты;
- комментарии;
- вложения;
- версии КП.

## 14.2. Выбор производителей

Режимы:

- адресный — 1–3 производителя;
- открытый — всем верифицированным производителям, соответствующим подбору.

## 14.3. История

Неизменяемо хранится:

- RFQ;
- изменения;
- комментарии;
- версии предложений;
- версия калькулятора.

## 14.4. Reverse auction

Обратный multi-vendor auction — **вторая очередь**.

Но модель первой очереди должна не блокировать его добавление.

# 15. Скидочный workflow

Целевой сценарий:

1. покупатель вводит желаемую скидку;
2. скидка запрашивается от DDP по правилам контракта;
3. продавец/производитель принимает решение;
4. формируется новое КП либо отказ;
5. если снижение невозможно, показывается сообщение о максимальной доступной цене;
6. покупатель принимает или отказывается.

До стадии сделки производитель должен работать с `buyer_code`, а не с раскрытым лидом, если заказчик сохраняет это требование в финальном ТЗ.

После `Заключение сделки`:

- формируется протокол условий;
- лид раскрывается Оператору/по правилам системы;
- audit log получает событие `lead.revealed`.

Статус: **целевое требование нового CPQ-документа, не считать полностью реализованным в baseline 4.4.4**.

# 16. Инженерный опросник — принцип продукта

## 16.1. Почему опросник теперь необязательный

Инженер заказчика отметил UX-риск: длинная обязательная форма снижает конверсию и создаёт проблемы при обрыве соединения.

Принято решение разделить два сценария:

### Сценарий A — «Заказать лебёдку»

Короткий коммерческий лид.

Не требует заполнения инженерной простыни.

### Сценарий B — «Заполнить опросный лист»

Расширенная инженерная форма для тех, кому требуется техническое уточнение/проработка.

## 16.2. Две отдельные CTA

В карточке:

- **Заполнить опросный лист**;
- **Заказать лебёдку**.

Нельзя снова объединять их в один обязательный путь.

Страница прямого заказа должна собирать только минимально необходимую информацию.

Пример состава:

- контакт;

- выбранная модель/исполнение;
- количество партии;
- желаемый срок производства/поставки;

## 17.1. Коммерческий блок

Название:

**Коммерческий запрос и поставка**

Текст, подтверждённый заказчиком:

> Запрос на индивидуальное ценовое предложение в зависимости от количества партии лебёдок и сроков производства.

# 20. UX опросника

## 20.1. Не «простыня»

Запрещено возвращаться к одному длинному столбцу 100+ полей.

Требования:

- блоки/аккордеоны;
- 2 поля в строке на desktop;
- адаптивно 1 поле на мобильном;
- краткие пояснения;
- схемы рядом;
- известные данные не спрашивать повторно.

## 20.2. Автоподстановка

Источники:

- выбранные фильтры;
- модель;
- конкретное исполнение;
- уже введённые данные проекта.

Автоподставленное значение должно визуально отличаться/иметь отметку.

## 20.3. Неизвестные поля

Техническое поле разрешено оставить пустым, если пользователь его не знает.

Нельзя превращать UNKNOWN в искусственный обязательный ввод только ради формы.

## 20.4. Черновик

Чтобы пользователь не заполнял всё заново:

- локальное автосохранение;
- серверный draft;
- draft token в URL;
- восстановление после reload;
- кнопка `Сохранить и продолжить позже`.

Целевое улучшение:

- информировать о статусе `Сохранено` / `Нет соединения, сохранено локально`;
- синхронизировать при восстановлении связи.

## Подтверждённые замечания инженера — 27.08.2026 (v4.4.4)

В инженерном опроснике обязательны следующие правила:

1. Пользовательские подписи и подсказки должны быть однозначными и инженерно понятными; рядом со сложными параметрами приводится пример или пояснение, что именно измерять/выбирать.
2. Пользовательский интерфейс использует систему СИ. Футы, фунты и дюймы из оригинального американского TDNA Survey не используются как единицы ввода. Геометрические размеры задаются в мм, длины — в м, масса — в кг, ускорение — в м/с².
3. Поле 208–230 / 460–480 называется «Выходное напряжение привода, В», а не «мощность».
4. Для параметров, завязанных на эскизы Torin, интерфейс явно показывает ссылку «См. рис. N».
5. Каждый эскиз в опроснике увеличивается по клику в полноэкранном lightbox; закрытие — кнопкой, кликом по фону или Esc.
6. Неоднозначное поле «Расположение существующей закладной балки под лебёдку» заменено понятным выбором схем A–E из Torin Illustration 3 с пояснением.
7. Трос Боудена называется «Устройство дистанционного растормаживания». Он находится в инженерном опроснике рядом с длиной кабеля энкодера, а не в калькуляторе. Значения: «Не требуется», «8 м (стандарт)», «10 м», «12 м». Правило действует как для машинного помещения, так и для MRL.
8. Опросник остаётся необязательным: пользователь может сразу выбрать «Заказать лебёдку» и отправить короткий коммерческий запрос.


## Терминологическая правка инженера — 27.08.2026 (v4.4.4)

В разделе «Блоки / шкивы» поле `tdna_sheave_type` отображается пользователю как **«Тип отводного блока / схема огибания канатом»**. Англоязычные варианты Torin не показываются без перевода. Допустимые варианты UI:

- **A — Отводной блок, угол охвата < 90°**;
- **B — Угол охвата 90°**;
- **C — Угол охвата 180°**.

Источник геометрии — оригинальный эскиз Torin Drive (страница с вариантами A/B/C). Эскиз остаётся доступен в форме и увеличивается по клику. Внутренний код поля `tdna_sheave_type` не меняется, чтобы не ломать сохранённые черновики и существующие заявки.


# Актуализация v4.4.5 — 27.08.2026 — сокращение инженерного опросника

## Подтверждённое UX-требование

После выбора конкретного исполнения пользователь не должен повторно вводить технические параметры, которые платформа уже знает. Цель — сократить форму и снизить вероятность противоречий между подбором и вручную введёнными ответами.

## Реализовано

Перед расширенной технической частью добавлен read-only блок **«Параметры выбранного исполнения»**. Он показывает:

- производителя;
- модель / исполнение;
- ID исполнения;
- тип лебёдки;
- тип размещения;
- форму лебёдки;
- кратность подвески;
- грузоподъёмность;
- скорость;
- диаметр каната.

Из редактируемой формы удалены дублирующие поля TDNA: `tdna_car_id`, `tdna_winch_type`, `tdna_location`, `tdna_suspension`, `tdna_capacity`, `tdna_speed`, `tdna_machine_shape`, `tdna_existing_rope_diameter`, `tdna_serial`.

Количество полей расширенного инженерного schema уменьшено с **67 до 58**. При этом значения не теряются: заявка по-прежнему хранит `product_id` и полный `product_snapshot` выбранного исполнения.

Исторические заявки и черновики, созданные до v4.4.5 и содержащие старые ключи, не удаляются и не переписываются.

## Что остаётся в ручной технической части

Только данные, которые не определяются выбранным исполнением автоматически: параметры существующего объекта, требования к приводу, длина кабеля энкодера, устройство дистанционного растормаживания, системные параметры, комплектация КП, монтажные размеры и схемы рис. 1–4, параметры отводных блоков/шкивов и дополнительные препятствия.


## v4.4.6 — медиабиблиотека оборудования

Реализована управляемая медиабиблиотека без привязки к правке кода.

Правила наследования медиа:

1. `execution` — конкретное исполнение имеет наивысший приоритет;
2. `model` — если у исполнения нет своего фото, используются материалы модели;
3. `family` — если у модели нет собственного материала, используется семейство производителя;
4. старое `image_ref` остаётся безопасным fallback для обратной совместимости.

Одна модель/семейство/исполнение может иметь несколько материалов. Поддерживаемые типы: `photo`, `drawing`, `document`. Для фото можно назначить основное изображение и порядок сортировки. Основное фото автоматически используется в каталоге, карточке и сравнении.

Добавлена таблица SQLite `media_assets` со связями `manufacturer / family / model / product_id`, типом материала, URL, названием, признаком основного фото и сортировкой. При первом запуске существующие изображения из `image_ref` и сохранённые семейные файлы `/static/winches` автоматически регистрируются в медиабиблиотеке.

Администратор получает страницу `/admin/media`, где можно загрузить JPG/JPEG/PNG/WEBP/GIF/SVG/PDF, выбрать уровень привязки, тип материала, основное фото и порядок. В карточке позиции из `/admin` добавлена ссылка `Медиа`.

Публичный API `/api/products/{id}` теперь отдаёт `media`, `media_family`, `primary_image`; `/api/products/{id}/media` возвращает разрешённую галерею. Карточка оборудования показывает галерею `Фото / Чертежи / Документы`.

Важно для обновлений: вместе с БД необходимо сохранять оба каталога `/app/static/winches` и `/app/static/media-library`. Загруженные файлы не удаляются физически при удалении привязки из БД, чтобы не разрушать исторические snapshots заявок.
