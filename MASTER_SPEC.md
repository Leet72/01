# UX RULE v4.2 — Модель и исполнение

**Источник истины:** техническая база хранит исполнения; пользовательский каталог показывает модели.

1. Подбор применяется к каждой из 838 строк-исполнений отдельно.
2. FAIL исключает исполнение; UNKNOWN не исключает и требует уточнения.
3. После подбора оставшиеся исполнения группируются по `manufacturer + model`.
4. Одна модель отображается одной карточкой.
5. Карточка показывает число доступных исполнений и диапазоны параметров.
6. Перед сравнением, расчётом или запросом цены инженер выбирает конкретное исполнение.
7. Нельзя объединять разные значения в вымышленную «среднюю» спецификацию модели.
8. Все исходные raw-поля сохраняются и доступны в техническом паспорте исполнения.

## UX-правило v4.4.5 — не спрашивать повторно уже известные параметры

Подтверждено заказчиком 27.08.2026. Расширенный инженерный опросник не должен повторно запрашивать значения, которые уже однозначно известны из выбранного исполнения/подбора.

Вместо ручных полей перед технической частью показывается компактный блок **«Параметры выбранного исполнения»**. В него входят: производитель, модель/исполнение, ID исполнения, тип лебёдки, тип размещения, форма, кратность подвески, грузоподъёмность, скорость и диаметр каната.

Из ручного опросника удалены как дубли:
- идентификационный номер лебёдки;
- тип лебёдки;
- расположение / тип размещения;
- кратность подвески;
- грузоподъёмность;
- скорость;
- форма лебёдки;
- диаметр установленного каната, когда используется выбранное исполнение как источник;
- повторный «серийный номер лебёдки» из чертёжного раздела.

Источником этих значений остаётся snapshot выбранного исполнения в заявке. Исторические заявки/черновики со старыми кодами полей не удаляются и остаются читаемыми.

## 1. Назначение

Профессиональный B2B-каталог и инженерный конфигуратор лифтовых лебёдок. Это не интернет-магазин для массового покупателя. Основной пользователь — инженер/технический специалист.

Основной сценарий:

Параметры проекта → инженерный подбор → список кандидатов → сравнение 2–4 моделей → техническая карточка → расчёт стоимости → запрос цены → предзаполненный опросный лист → заявка.

## 4. Объяснимый движок подбора

Каждый выбранный параметр оценивается в одном из трёх состояний:

- PASS — значение в базе известно и соответствует условию;
- UNKNOWN — значение в исходниках отсутствует; модель НЕ исключается, а помечается «Требует уточнения»;
- FAIL — значение известно и противоречит условию; модель исключается.

Поэтому отсутствие данных больше не означает «модель не подходит».

Выдача сортируется:
1. полностью подтверждённые модели;
2. кандидаты с минимальным количеством неизвестных полей.

Для каждой карточки API возвращает:
- `match_status`;
- `match_summary`;
- `match_checks`;
- `clarifications`.

## 5. Согласованные фильтры

1. Производитель — точное значение.
2. Тип лебёдки — редукторная / безредукторная таблетка / безредукторная бочонок.
3. Грузоподъёмность — точные значения.
4. Скорость — диапазоны с включительными границами.
5. Кратность подвески — допустимые значения.
6. Количество скоростей — 1 или 2. У безредукторных автоматически 1.
7. Наличие ЧП — Да / Нет.
8. Энкодер — Инкрементальный / Абсолютный / Нет.
9. Мощность — диапазоны с включительными границами.
10. Максимальная консольная нагрузка — требуемая нагрузка <= допустимой модели; если данных нет — UNKNOWN.
11. Максимальная высота подъёма — требуемая высота <= допустимой модели; если данных нет — UNKNOWN.
12. Форма ручья — U / V.
13. Угол подреза — U: 90/95/100/105; V: 45.
14. Диаметр КВШ — точное значение.
15. Количество канатов — точное допустимое значение.
16. Диаметр канатов — точное допустимое значение.
17. Число включений в час — точное значение.
18. Напряжение питания тормоза — нормализованные варианты.
19. Масса — точное значение.
20. Тип размещения — в машинном помещении / без машинного помещения. Если не заполнен — UNKNOWN.

Передаточное число и дистанционное расцепление сохраняются в БД; инженерная логика может быть включена после подтверждения данных.

## 5.1. Подтверждённое правило «Тип размещения» — 26.08.2026

Правило является частью инженерного ТЗ:

- `Без машинного помещения`: все «бочонки» + плоские таблетки `WE 06`, `WE 10`, `WE 20`, `WJC-*-T`;
- `В машинном помещении`: остальные «Безредукторные таблетки» (объёмные таблетки);
- явно заданное администратором/источником значение имеет приоритет;
- неклассифицированные типы остаются UNKNOWN.

Правило обязано одинаково работать в БД, фильтре, карточке, API и админке. При запуске legacy-БД пустые значения безопасно материализуются, ручные значения не перезаписываются. Текущее покрытие: 832/838 исполнений (MRL 498, MR 334, UNKNOWN 6).

## 26.08.2026 — RFQ / инженерный опросник Torin Drive

Заказчик передал новое UX-требование к опросному листу после консультации с инженером.

### Источники

- TDNA Traction Survey (Torin Drive North America): `https://torindrivena.com/api/sp/view/WebsiteAsset/TDNA%20Traction%20Survey.pdf?dir=Survey/Machines`.
- Переведённый заказчиком документ «для воплощения на сайте-1.docx» должен использоваться как источник русскоязычного текста **кроме зачёркнутых фрагментов**. На момент сборки v4.4.0 сам файл не был приложен к проектному архиву, поэтому точная замена формулировок выполняется после получения файла без изменения архитектуры формы.
- Уже существующий опросный лист из исходного Excel остаётся источником полей и автозаполнения.

### Принятое UX-решение

Опросный лист не должен быть обязательной длинной формой для первичного лида. Используется двухуровневый сценарий:

1. **Короткий запрос:** имя, компания, телефон, e-mail, количество лебёдок, желаемый срок, комментарий.
2. **Расширенный инженерный опросник:** открывается по желанию и разбивается на визуальные тематические секции.

Часть известных значений автоматически переносится из выбранной модели и текущих фильтров. Неизвестные инженерные параметры можно оставить пустыми.

### Эскизы

В технических секциях показываются адаптированные web-схемы по логике TDNA Traction Survey:

- MR / MRL и размещение машины;
- привязка канатов к стенам, X1 / X2 / X3;
- отклоняющий/отводной блок, Ddef и Ys;
- габариты, высота помещения, Z1 / Z2 и препятствия.

Схемы являются оригинальными web-SVG платформы, а не скриншотами PDF. Это обеспечивает читаемость на мобильных устройствах и возможность дальнейшей локализации подписей.

### Защита от потери данных

Форма обязана сохранять черновик автоматически:

- локально в браузере после изменения поля;
- на сервере в таблице `inquiry_drafts`;
- черновик имеет токен и добавляется в URL как `?draft=...`, поэтому страницу можно обновить и продолжить заполнение;
- есть явная кнопка «Сохранить и продолжить позже»;
- при успешной отправке временный черновик удаляется.

Кратковременный обрыв сети не должен приводить к потере уже введённых данных: локальная копия продолжает сохраняться и серверная синхронизация возобновляется при доступности API.

### Коммерческий запрос и поставка

Блок сохраняется. Финальная формулировка заказчика:

> «Запрос на индивидуальное ценовое предложение в зависимости от количества партии лебёдок и сроков производства».

В блоке предусмотрены количество партии и требуемая дата/срок производства. Данные сохраняются вместе с RFQ.

### Правило конверсии

Минимум полей на первом шаге имеет приоритет над полнотой инженерного опросника. Полная техническая форма предназначена для квалификации уже заинтересованного лида, а не как барьер перед первым обращением.


## 26.08.2026 — точный опросник Torin Drive (v4.4.0)

Получены и приняты как источники требований:

- `для воплощения на сайте-1.docx` — русский перевод опросника;
- `TDNA Traction Survey.pdf` — оригинальный опросник и инженерные эскизы;
- `TDNA Traction Survey (2).pdf` — дубликат/копия оригинального источника.

Правило переноса: **текст полей берётся из переведённого DOCX, полностью зачёркнутые пункты не выводятся пользователю, эскизы берутся из оригинального PDF Torin Drive**.

В переведённом DOCX полностью зачёркнуты и поэтому исключены из расширенной инженерной формы:

4. Адрес месторасположения проекта;
5. Консультант.

Эти сведения не должны повторяться внутри инженерных разделов. Контактная/коммерческая информация собирается коротким первым шагом RFQ.

Расширенная форма v4.4 содержит 66 полей в 6 визуальных группах:

1. Основные параметры подбора;
2. Системные параметры (если известно);
3. Комплектация для расчёта цены;
4. Данные для чертежа;
5. Отводной блок и компоновка;
6. Блоки / шкивы.

Используются оригинальные схемы Torin: левое/правое положение машины, план/вид машинного помещения с Rope Drop и Z1/Z2, балки/CT/Wf/Ww/Ddef/Ys, угловые схемы A/B/C/D с X1/X2/X3, типы обхвата и размеры L1–L6.

UX-правила:

- поля из выбранного исполнения и фильтров подставляются автоматически;
- неизвестный параметр разрешено оставить пустым;
- повторяющиеся сведения не спрашиваются заново;
- техническая часть не обязательна для первого лида;
- черновик сохраняется локально и на сервере;
- после восстановления страницы заполненные значения восстанавливаются;
- блок «Коммерческий запрос и поставка» остаётся отдельным финальным блоком.

## 26.08.2026 — разведение инженерного опросника и заказа
Заказчик передал замечание инженера: полный опросный лист не должен быть обязательным для каждого покупателя. В пользовательском интерфейсе необходимо разделить два сценария:
1. **Заполнить опросный лист** — добровольный расширенный инженерный сценарий для проектов, где требуются чертёжные размеры, компоновка, отводной блок и прочие технические уточнения. Должны сохраняться TDNA-эскизы, автозаполнение и черновик.
2. **Заказать лебёдку** — короткий коммерческий сценарий без обязательного технического опросника. Минимум: контакт, компания, количество партии, желаемый срок производства и комментарий.

Блок **«Коммерческий запрос и поставка»** сохраняется. Текст: **«Запрос на индивидуальное ценовое предложение в зависимости от количества партии лебёдок и сроков производства»**.

Правило UX: ни каталог, ни расчёт стоимости, ни запрос коммерческого предложения не должны принуждать покупателя к заполнению полного инженерного опросника.


## Подтверждённые замечания инженера — 27.08.2026 (v4.4.4)

В инженерном опроснике обязательны следующие правила:

1. Пользовательские подписи и подсказки должны быть однозначными и инженерно понятными; рядом со сложными параметрами приводится пример или пояснение, что именно измерять/выбирать.
2. Пользовательский интерфейс использует систему СИ. Футы, фунты и дюймы из оригинального американского TDNA Survey не используются как единицы ввода. Геометрические размеры задаются в мм, длины — в м, масса — в кг, ускорение — в м/с².
3. Поле 208–230 / 460–480 называется «Выходное напряжение привода, В», а не «мощность».
4. Для параметров, завязанных на эскизы Torin, интерфейс явно показывает ссылку «См. рис. N».
5. Каждый эскиз в опроснике увеличивается по клику в полноэкранном lightbox; закрытие — кнопкой, кликом по фону или Esc.
6. Неоднозначное поле «Расположение существующей закладной балки под лебёдку» заменено понятным выбором схем A–E из Torin Illustration 3 с пояснением.
7. Трос Боудена называется «Устройство дистанционного растормаживания». Он находится в инженерном опроснике рядом с длиной кабеля энкодера, а не в калькуляторе. Значения: «Не требуется», «8 м (стандарт)», «10 м», «12 м». Правило действует как для машинного помещения, так и для MRL.
8. Опросник остаётся необязательным: пользователь может сразу выбрать «Заказать лебёдку» и отправить короткий коммерческий запрос.


## Терминологическая правка инженера — 27.08.2026 (v4.4.4)

В разделе «Блоки / шкивы» поле `tdna_sheave_type` отображается пользователю как **«Тип отводного блока / схема огибания канатом»**. Англоязычные варианты Torin не показываются без перевода. Допустимые варианты UI:

- **A — Отводной блок, угол охвата < 90°**;
- **B — Угол охвата 90°**;
- **C — Угол охвата 180°**.

Источник геометрии — оригинальный эскиз Torin Drive (страница с вариантами A/B/C). Эскиз остаётся доступен в форме и увеличивается по клику. Внутренний код поля `tdna_sheave_type` не меняется, чтобы не ломать сохранённые черновики и существующие заявки.


## v4.4.6 — медиабиблиотека оборудования

Реализована управляемая медиабиблиотека без привязки к правке кода.

Правила наследования медиа:

1. `execution` — конкретное исполнение имеет наивысший приоритет;
2. `model` — если у исполнения нет своего фото, используются материалы модели;
3. `family` — если у модели нет собственного материала, используется семейство производителя;
4. старое `image_ref` остаётся безопасным fallback для обратной совместимости.

Одна модель/семейство/исполнение может иметь несколько материалов. Поддерживаемые типы: `photo`, `drawing`, `document`. Для фото можно назначить основное изображение и порядок сортировки. Основное фото автоматически используется в каталоге, карточке и сравнении.

Добавлена таблица SQLite `media_assets` со связями `manufacturer / family / model / product_id`, типом материала, URL, названием, признаком основного фото и сортировкой. При первом запуске существующие изображения из `image_ref` и сохранённые семейные файлы `/static/winches` автоматически регистрируются в медиабиблиотеке.

Администратор получает страницу `/admin/media`, где можно загрузить JPG/JPEG/PNG/WEBP/GIF/SVG/PDF, выбрать уровень привязки, тип материала, основное фото и порядок. В карточке позиции из `/admin` добавлена ссылка `Медиа`.

Публичный API `/api/products/{id}` теперь отдаёт `media`, `media_family`, `primary_image`; `/api/products/{id}/media` возвращает разрешённую галерею. Карточка оборудования показывает галерею `Фото / Чертежи / Документы`.

Важно для обновлений: вместе с БД необходимо сохранять оба каталога `/app/static/winches` и `/app/static/media-library`. Загруженные файлы не удаляются физически при удалении привязки из БД, чтобы не разрушать исторические snapshots заявок.

## v4.4.9 — Explicit Execution Selector / различия исполнений

Подтверждённое UX-замечание заказчика: когда одна модель содержит несколько исполнений, пользователь должен однозначно понимать, как переключать исполнения и чем они отличаются.

Реализовано:
- вся строка исполнения кликабельна;
- добавлен явный radio-индикатор выбора и бейдж «Выбрано»;
- выбранная строка визуально подсвечивается;
- текст прямо сообщает, что выбранное исполнение используется для расчёта, опросного листа и заказа;
- таблица автоматически показывает только те нормализованные технические характеристики, значения которых реально различаются между исполнениями данной модели;
- различающиеся ячейки визуально выделяются;
- управление доступно мышью и клавиатурой Enter/Space;
- при переключении заново загружается полный product record конкретного `product_id`, поэтому медиатека, технический паспорт, сравнение, калькулятор, опросник и заказ работают с выбранным исполнением.

Контрольный пример из текущей БД: модель `WE 06-630-100(400)` содержит исполнения `#360` и `#395`. Их видимые базовые параметры совпадают, но масса различается: `280 кг` против `310 кг`. В v4.4.9 таблица автоматически показывает именно столбец «Масса», не заставляя пользователя искать отличие вручную.
